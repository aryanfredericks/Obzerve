Observability for AI agents · open source · self-hosted

See what your agent did, replay it, and stop it from happening again.

Obzerve records every agent request as a trace of its LLM calls, tool calls, retrieval and handoffs. You get latency, errors, tokens and estimated cost for each step. When a request goes wrong, you can replay it exactly, turn it into a regression test, and block the next release that breaks it.

API keys and the dev key

Version 0.1.0 has no user accounts yet. Everything authenticates with a project API key, and local setups come with a ready-made one.

The dev key

make stack-demo and make bootstrap create a project called demo with the key dev_project_key. That key has every scope, so you can use it right away for:

  • sending traces from the SDK or the demo agent,
  • the dashboard (make stack-demo builds the key into it),
  • the obzerve CLI: export OBZERVE_API_KEY=dev_project_key.
Local only

The dev key is public: it's written in this page and in the repository. Use it on your own machine only. Anything reachable by other people needs its own project keys, created as shown below.

Project keys

Each project keeps its traces, datasets and prices separate. A key belongs to one project and carries scopes:

ScopeAllowsGive it to
ingestSending traces (POST /v1/traces)Agents in production
readThe dashboard and query API: traces, metrics, replay bundlesPeople viewing the dashboard
writeRegistering prompt versions, creating regression cases, submitting eval runsCI pipelines, engineers running evals
bash
# containers: run inside the API container
podman compose --profile stack exec api obzerve-server create-project my-app
# development setup
uv run obzerve-server create-project my-app

# another key for the same project, e.g. ingest-only for production
uv run obzerve-server create-key my-app --scopes ingest

The key is printed once. Only a hash is stored, so keep it somewhere safe.

  • SDK: pass it as api_key=.
  • CLI: set it as OBZERVE_API_KEY.
  • Dashboard: enter it under API key in the top bar. It's stored in your browser.

Requests send the key as Authorization: Bearer <key> or as X-API-Key: <key>.

User accounts and login are planned for 0.1.1.

Clone the repo and try it

The fastest way to see Obzerve working: the whole platform in containers, plus a demo research agent that fails and gets fixed. It works offline with a built-in mock LLM, in about 15 minutes.

What you need

ToolCheckUsed for
Gitgit --versionGetting the code
Docker or Podman, with Composedocker compose versionRunning the platform
uvuv --versionThe demo agent and CLI
makemake --versionShortcuts (each target is a plain command in the Makefile)

The demo agent installs PyTorch (about 4 GB) for its retrieval step. It uses an AMD GPU through ROCm when one is present, and otherwise falls back to the CPU.

Start the platform

  1. Get the code and start everything. The first build takes a few minutes.
    bash
    git clone https://github.com/aryanfredericks/Obzerve.git
cd Obzerve
make stack-demo     # PostgreSQL, Redis, API, worker, dashboard + the dev key
  2. Check it is healthy, then open localhost:8080.
    bash
    curl http://localhost:8000/readyz
# {"status":"ok","database":"ok","queue":"ok"}
  3. Point the tools at it in every terminal you use:
    bash
    export OBZERVE_ENDPOINT=http://localhost:8000
export OBZERVE_API_KEY=dev_project_key
export OBZERVE_DASHBOARD_URL=http://localhost:8080

Watch a failure, then fix it

  1. Run the agent normally, and once with every LLM call failing. The failing run prints run failed: … (simulated timeout, injected fault); that's expected.
    bash
    uv sync    # first time only: installs the demo agent
TRACE_OK=$(uv run research-agent --quiet | grep -oP 'traces/\K[0-9a-f]{32}')
TRACE_FAIL=$(uv run research-agent --fault llm-outage --quiet | grep -oP 'traces/\K[0-9a-f]{32}')
echo "$OBZERVE_DASHBOARD_URL/traces/$TRACE_FAIL"

    The trace page shows the timeline, three failed LLM attempts with their retries, and a callout naming the root cause.

  2. Replay it. Every step is served from the recording, so the failure happens again exactly and nothing is called. Then replay the same recording with a fix:
    bash
    uv run research-agent replay "$TRACE_FAIL" --mode recorded --quiet   # fails the same way
uv run research-agent replay "$TRACE_FAIL" --mode recorded --fallback # now degrades gracefully
  3. Make both traces regression cases, then compare baseline and fix:
    bash
    uv run obzerve case add "$TRACE_FAIL" --dataset getting-started \
    --name "LLM outage degrades gracefully" --mode recorded --no-error --contains-any unavailable
uv run obzerve case add "$TRACE_OK" --dataset getting-started \
    --name "Answers the question" --no-error --contains-any evaluation

BASE=$(uv run research-agent eval getting-started --label baseline | grep -oP '^run: \K\S+')
FIX=$(uv run research-agent eval getting-started --label "fallback fix" --fallback | grep -oP '^run: \K\S+')
uv run obzerve eval gate "$BASE" "$FIX" --min-pass-rate 1.0   # GATE PASSED, exit 0
uv run obzerve eval gate "$FIX" "$BASE"                       # GATE FAILED, exit 1

Other failures to try with --fault:

  • llm-timeout: recovers after retries.
  • bad-retrieval: every step "succeeds", but the evidence is irrelevant.
  • search-error: a tool fails and the agent carries on without it.

Add --llm ollama to use a real local model (see Troubleshooting for Qwen3 settings).

Stop everything

make stack-down stops every Obzerve container, including extra workers. Your data stays in the obzerve-pgdata volume. The full walkthrough, with expected output for each step, is in docs/getting-started.md.

Monitor your agent with pip install obzerve

Add the SDK to your own project. Wrap each request in a trace, and every model call made through a supported client library is traced automatically.

Install

bash
pip install obzerve                       # or: uv add obzerve
pip install "obzerve[openai,anthropic]"   # with the client libraries you use
# extras: openai, anthropic, huggingface, transformers, all

You need Python 3.10 or newer and an Obzerve server (run one locally or self-host). You also need a project key; on your own machine, the dev key works.

Trace a request

python
from obzerve import Observer

observer = Observer(
    endpoint="http://localhost:8000",
    api_key="dev_project_key",          # a project key outside local development
    service_name="support-bot",
)
observer.instrument()                   # trace OpenAI, Anthropic and Hugging Face calls

def handle(ticket: str) -> str:
    with observer.trace("support_bot", input={"ticket": ticket}) as trace:
        answer = run_my_agent(ticket)   # every LLM call inside becomes a span of this trace
        trace.set_output(answer)
        return answer

Open the dashboard: each call to handle is one trace.

What is traced automatically

LibraryCovered
openaiChat Completions, Responses and Embeddings: sync, async and streaming. OpenAI-compatible servers (vLLM, Ollama, TGI, LM Studio) are recorded as openai_compatible, with their address.
anthropicmessages.create (including stream=True) and messages.stream(), sync and async. Prompt-cache reads are counted as cached tokens.
huggingface_hubInferenceClient.chat_completion, also reached as client.chat.completions.create, and text_generation. Covers the hosted Inference API, Inference Endpoints and self-hosted TGI.
transformersgenerate() on any local model (model, device, prompt and generated tokens) and text-generation pipelines.

Each model call records:

  • model and provider,
  • sampling settings,
  • input, output and cached tokens,
  • finish reason,
  • the prompt and response (redacted).

Choose libraries explicitly with observer.instrument(openai=True, anthropic=False). Undo it with handle = observer.instrument(); handle.uninstrument().

transformers loads PyTorch on import, so by default it's instrumented only if your code has already imported it. Pass transformers=True to force it.

Safe by default
  • Your call never breaks: if a library changes shape, the trace loses detail but the request still succeeds.
  • Telemetry never blocks: it's sent in the background through a bounded buffer. If the server is down, spans are dropped instead of blocking your agent. observer.stats() shows exactly how many were sent, failed or dropped.
  • Secrets are redacted: values such as api_key, password and bearer tokens. Turn payload capture off entirely with Observer(capture_payloads=False).

Streamed responses are one span that stays open until you finish reading the stream, close it, or leave its with block. Close streams you abandon early.

Your own tools and steps

python
from obzerve import SpanKind

with observer.span("search_orders", kind=SpanKind.TOOL, input={"customer": cid}) as span:
    orders = orders_api.search(cid)
    span.set_output(orders)

@observer.observe(kind=SpanKind.RETRIEVAL)     # decorator form, sync or async
def retrieve(query: str) -> list[str]: ...

# a model call the instrumentation doesn't cover
with observer.span("llm.generate", kind=SpanKind.LLM) as span:
    reply = my_client.generate(prompt)
    span.set_llm(model="my-model", provider="acme", input_tokens=812, output_tokens=95)
  • Errors: an exception inside a span marks it as failed and records the error type and message.
  • Retries: span.record_retry(attempt, exc) records each retry.
  • Across services: observer.inject_headers() on the caller and observer.trace(..., parent_headers=headers) on the callee join both sides into one trace.

The SDK README lists every option.

Replay and regression tests

Reproduce a production request exactly, without calling any model or tool. Then keep it as a test that every future change must pass.

Make steps replayable

Calls through the instrumented libraries are recorded automatically. For your own tools, use @observer.replayable. Mark anything that changes the outside world as a side effect: a replay never runs it again.

python
@observer.replayable(kind=SpanKind.TOOL)
def lookup_order(order_id: str) -> dict: ...

@observer.replayable(kind=SpanKind.TOOL, side_effect=True)   # never re-run by a replay
def refund(order_id: str) -> None: ...

# custom types need encode/decode to and from JSON
@observer.replayable(kind=SpanKind.RETRIEVAL,
                     encode=lambda docs: [d.to_dict() for d in docs],
                     decode=lambda data: [Doc(**d) for d in data])
def retrieve(query: str) -> list[Doc]: ...

Each trace is labelled replayable, partially replayable or not replayable. The trace page says why.

Replay a trace

python
from obzerve.client import ObzerveClient
from obzerve.replay import RECORDED, LLM_LIVE

client = ObzerveClient("http://localhost:8000", "dev_project_key")
bundle = client.replay_bundle(trace_id)

with observer.replay(bundle, RECORDED):        # nothing external is called
    handle(**bundle.root_input)                # the replay is linked to the original trace
PolicyRuns liveUse it to
RECORDEDNothingReproduce the request exactly, including its failures
LLM_LIVEModel callsTest a new prompt or model against the recorded tool and retrieval results
LIVEEverything except side effectsCheck the whole workflow under current conditions

If a replay calls a step with different inputs than the recording, the step is flagged as diverged. The dashboard compares the original and the replay step by step.

Streamed responses are traced but not recorded yet. A RECORDED replay that reaches one stops with a clear error.

Turn it into a regression case

Use Turn into a regression case… on the trace page, or the CLI:

bash
obzerve case add <trace_id> --dataset regressions --name "refund flow" \
    --mode recorded --no-error --contains-any refunded

A case keeps a frozen copy of the trace's recordings, so it outlives the trace. Each case has its own mode:

  • recorded: a failure that must reproduce exactly.
  • llm-live: checks on answer quality.

Assertions are deterministic:

  • --no-error
  • --contains-all, --contains-any, --not-contains
  • --regex
  • --max-latency-ms

Run a dataset against a change

python
from obzerve.evals import run_eval

prompt = client.register_prompt("support-bot", {"system": SYSTEM_PROMPT, "model": "gpt-x"})
run = run_eval(
    observer, client, "regressions",
    target=lambda root_input: handle(**root_input),   # your agent's entry point
    label="new-system-prompt",
    prompt_version=prompt,                             # recorded with the run
)
print("run:", run["run"]["id"], "pass rate", run["run"]["pass_rate"])

Each run records the dataset version, evaluator version, prompt version and replay policy. Two runs are only marked comparable when all of those match.

Gate releases in CI

Block a prompt, model or code change that makes a passing case fail. obzerve eval gate exits with 1 when the candidate doesn't meet your criteria.

yaml
# .github/workflows/agent-evals.yml (excerpt)
- run: pip install obzerve
- name: Evaluate the candidate
  env:
    OBZERVE_ENDPOINT: ${{ secrets.OBZERVE_ENDPOINT }}
    OBZERVE_API_KEY: ${{ secrets.OBZERVE_API_KEY }}   # a key with read + write scopes
  run: |
    CANDIDATE=$(python evals/run.py --label "$GITHUB_SHA")   # prints the run id
    obzerve eval gate "${{ vars.BASELINE_RUN }}" "$CANDIDATE" \
        --max-regressions 0 --max-pass-rate-drop 0
OptionFails when
--max-regressions NMore than N cases that passed in the baseline fail now (default 0)
--min-pass-rate RThe candidate's pass rate is below R (0–1)
--max-pass-rate-drop RThe pass rate fell by more than R
--max-cost-increase-pct PEstimated cost per case rose by more than P percent
--max-p95-latency-increase-pct Pp95 latency rose by more than P percent

Runs that aren't comparable (a different dataset version, evaluator or replay policy) always fail the gate. obzerve eval compare A B prints the same comparison without failing. The dashboard has it too: under Evals, tick two runs and choose Compare selected.

Already using OpenTelemetry

Obzerve accepts standard OTLP/HTTP traces, so any OpenTelemetry-instrumented app can send to it without the SDK.

bash
export OTEL_EXPORTER_OTLP_TRACES_ENDPOINT=http://localhost:8000/v1/traces
export OTEL_EXPORTER_OTLP_TRACES_HEADERS="x-api-key=dev_project_key"
export OTEL_EXPORTER_OTLP_TRACES_PROTOCOL=http/protobuf
  • Formats: protobuf or JSON, optionally gzip-compressed.
  • Model data: spans that use the OpenTelemetry GenAI conventions (gen_ai.request.model, gen_ai.usage.input_tokens, …) get model, token and cost figures.
  • Retries are safe: invalid spans are rejected one at a time, and re-sending a batch never double-counts.

Replay needs the SDK. Plain traces don't record results exactly, so those traces are marked not replayable.

If you also send the Anthropic SDK's own OpenTelemetry spans to Obzerve while using observer.instrument(), turn one of them off (Anthropic(open_telemetry=False)). Otherwise each call appears twice.

Self-host for a team

The compose file in the repository runs the whole platform with Docker Compose or Podman Compose.

bash
git clone https://github.com/aryanfredericks/Obzerve.git && cd Obzerve
echo "OBZERVE_DB_PASSWORD=$(openssl rand -hex 24)" > .env
make stack                    # dashboard :8080, API :8000 (no dev key, no demo data)
podman compose --profile stack exec api obzerve-server create-project my-team
ServiceRole
postgres, redisStorage, and the queue that buffers incoming telemetry
migrateApplies database migrations, then exits; the API and workers wait for it
apiReceives traces (queue mode) and serves the dashboard's API
workerWrites queued telemetry to the database; scale with --scale worker=3
webThe dashboard, with /api proxied to the API

Before exposing it

  • Put a TLS proxy (Caddy, Traefik or a load balancer) in front of web and api. Ports bind to 127.0.0.1 until you set OBZERVE_API_BIND or OBZERVE_WEB_BIND.
  • Change OBZERVE_DB_PASSWORD, and never set OBZERVE_DASHBOARD_KEY or use the dev key.
  • Keep /metrics (API) and port 9101 (workers) private. They're unauthenticated Prometheus endpoints.

Reliability: in queue mode, ingestion keeps working through database outages. When the backlog is full, clients get 503 with Retry-After, and nothing is lost. Workers scale linearly: in our test, one worker drained a 35k-trace backlog in 93 s, and three workers did it in 31 s.

Upgrades, backups and every setting are in docs/deployment.md.

Develop Obzerve

Estimated cost

LLM calls are priced as they arrive, from a table of per-model prices in US dollars per million tokens. Costs are estimates, not invoices.

bash
uv run obzerve-server pricing set gpt-x --provider openai --input 2.50 --output 10 --cached-input 1.25
uv run obzerve-server pricing set qwen3:latest --provider ollama --input 0 --output 0   # local: free
uv run obzerve-server pricing list
uv run obzerve-server pricing recompute        # re-price traces already stored
  • Effective dates: a price applies from its --effective-from date until a newer one.
  • Overrides: a --project or --provider price wins over a general one.
  • Unpriced calls: a call with tokens but no matching price is counted as unpriced, and the dashboard marks its total as partial.

In containers, run the commands with podman compose --profile stack exec api obzerve-server ….

Troubleshooting

SymptomFix
Dashboard says Not authorizedEnter a key under API key in the top bar (dev_project_key locally). make stack builds the dashboard without one.
obzerve CLI returns HTTP 401export OBZERVE_API_KEY=…; the CLI has no default key.
address already in useContainers and the development setup share ports 8000 and 5432. Stop one (make stack-down), or move the stack with OBZERVE_API_PORT / OBZERVE_WEB_PORT.
No traces appearCheck curl $OBZERVE_ENDPOINT/readyz and the key. observer.stats() shows whether spans failed or were dropped. Call observer.flush() before a short script exits.
This trace cannot be replayedThe trace has no replayable steps. Use observer.instrument() or @observer.replayable, then record a new one.
Qwen3 through Ollama's OpenAI endpoint returns empty textPass reasoning_effort="none". Otherwise the whole token budget goes to thinking (finish reason length).
The same Anthropic call appears twiceBoth Obzerve and the Anthropic SDK's own tracing reach Obzerve; use Anthropic(open_telemetry=False).
Server tests are skippedPostgreSQL or Redis isn't running: make db-up.
